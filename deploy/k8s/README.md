# K3s GitOps demo

This is a **separate** deployment of Aggregator. The existing serving
Docker Compose EC2 and its public DNS are not modified.

## Deployment pipeline

1. A push to `demo` triggers `.github/workflows/demo-deploy.yml`.
2. Code quality must pass; the workflow builds all eight application images
   and publishes each to GHCR with the 40-character source commit SHA.
3. After all images are available, `publish-k3s-release` copies the candidate
   manifests from `deploy/k8s` to **`deploy/k8s-live` in the same `demo`
   branch**, copies the monitoring provisioning files, updates eight image
   tags to that source SHA, and validates the rendered manifests.
4. Argo CD watches **`demo:deploy/k8s-live`**. It automatically syncs and
   self-heals these already-published Kubernetes manifests.
5. K3s ships with Traefik and ServiceLB enabled. A hostless HTTP Ingress
   routes port 80 to `aggregator-ui:3000`; that container's Caddy forwards
   the catalog, Product Health API, AI chat, Prometheus and Grafana paths.

The two directories in **one branch** are deliberate: Argo CD must not apply
untested candidate manifests while images are still being built. Edit
`deploy/k8s` as source; `deploy/k8s-live` is generated by the workflow.
Do not manually edit generated manifests.

A bot promotion commit touches only `deploy/k8s-live/**`, which is excluded
by the build workflow's `paths-ignore` (and GitHub normally does not trigger
new workflow runs from pushes made with `GITHUB_TOKEN`). This prevents
endless image-build loops. Stale build jobs refuse to overwrite later
`demo` commits; the push itself must be fast-forward.

The application stack includes Aggregator, Catalog, UI, AI Agent, Chaos
Maker, three dummy services, Prometheus and Grafana. Grafana contains the
demo timeline dashboard. Prometheus/Grafana data uses K3s local-path PVCs,
which are **not** durable if the EC2 instance is deleted.

## First deployment

- Review and apply policy updates in `deploy/infra/admin` using the
  authorized `infra-admin` identity; do not change IAM manually.
- Verify that all eight GHCR images allow **anonymous pulls**, since K3s has
  no image pull secret.
- Merge `dev` into `demo`, push, and confirm that
  `publish-k3s-release` created `deploy/k8s-live` in `demo`.
  **Known prerequisite:** the repository currently has active branch
  ruleset `demo` (ID 25923458) with `restrict updates`. The default
  `GITHUB_TOKEN` does **not** have an established bypass, so automatic
  promotion is expected to fail with the current settings. An explicitly
  authorized GitHub App/bypass or another reviewed publication mechanism
  must be configured before enabling the pipeline. Do not disable branch
  protection or infrastructure approvals as a workaround.
- For K3s provisioning, set `DEMO_INFRA_WORKFLOW_ENABLED=true`,
  `ENABLE_K3S_NODE=true`, and the existing `ENABLE_BEDROCK` value.
  The infrastructure workflow automatically passes its own Git SHA to
  the SSM-driven Ansible bootstrap; no SHA variable is needed.
- Review the OpenTofu plan and manually approve `demo-infra-apply`.
- Once the job succeeds, use OpenTofu output `k3s_public_ip` and open
  `http://<k3s_public_ip>/`. No DNS cutover is performed.

The infrastructure workflow waits for cloud-init/Ansible, K3s, Traefik,
Argo CD and its Aggregator Application to be healthy, and checks the HTTP
entrypoint and important APIs. SSM output is sent to CloudWatch Logs.

## Subsequent updates and rollback

Each successful `demo` image build publishes a new generated
`deploy/k8s-live` snapshot in the **same branch**. Argo CD sees only
the published state, so no re-running Ansible or direct SSH is required.
The `deploy` job in `demo-deploy.yml` still updates the separate Docker
Compose demo using SSM.

For rollback, revert the generated publication commit in `demo`; Argo CD
will return to the previous published release. Avoid triggering a fresh
image build while performing this rollback. Local PVC data is unaffected
by image rollback.

## Operating limits and security

- This demo deliberately serves **plain HTTP by IP**, not HTTPS.
  Neither DNS nor TLS certificates are configured. Port 443 is closed.
  Do not send secrets or sensitive data through this public endpoint.
- Argo CD, SSH and the Kubernetes API are not publicly exposed.
  The UI Caddy proxies Grafana/Prometheus routes; review their exposure
  before using any real workloads.
- Grafana's init container reads the public IPv4 from EC2 IMDSv2 to build
  its `/grafana/` URL. This depends on the Terraform hop limit; workload
  access to instance-profile credentials also needs hardening for
  production use.
- The default node is **t3.medium (4 GiB)**. It has **not** been proven
  sufficient for the entire stack. Watch pod OOMKills, node memory,
  CPU and scheduling; switch to a larger size if required.
- The first boot requires an already-published `deploy/k8s-live` manifest
  snapshot, public GHCR packages, outbound GitHub/GHCR connectivity and
  working containers. No AWS end-to-end K3s deployment has been tested yet.

## Diagnostics

Use the SSM command ID shown in GitHub Actions and the log group
`/aws/ssm/aggregator-demo-k3s`. In an SSM session:

```sh
sudo k3s kubectl get applications -n argocd
sudo k3s kubectl get pods,svc,ingress -n aggregator
sudo k3s kubectl top nodes
sudo k3s kubectl top pods -n aggregator
curl -i http://127.0.0.1/config.json
```

The `kubectl top` commands require a functioning Metrics Server, which
may take time to become ready on a new K3s node.
